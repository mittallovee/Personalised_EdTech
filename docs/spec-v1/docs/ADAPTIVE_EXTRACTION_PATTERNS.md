# Adaptive Extraction: Learn and Reuse Document Patterns

Consolidation note (18 October 2026): confirmed policy is retained below; concrete engineering defaults are in [technical proposals](TECHNICAL_DESIGN_PROPOSALS.md). Any remaining engine/library/quality choices are implementation evidence work, not additional required user questions.

Status: confirmed first-release scope on 18 October 2026. Samples will be supplied later; documentation continues now. No pattern engine, model integration or token-saving benchmark exists.

## Confirmed requirement

Many files share layout A, many others share layout B, and further layout families must be supported. AI understands/extracts an unfamiliar layout initially, saves a reusable versioned pattern, and automatically recognizes/reuses compatible patterns for subsequent files. The goal is faster processing and lower extraction AI-token usage while preserving quality. Support selectable documents, scans/photos, handwritten questions and handwritten solutions.

A pattern describes document structure, not merely a filename extension or one of the nine question types. One PDF can contain different page/section layouts and mixed question types. Existing input formats, size limits and normal review rules remain.

## Proposed workflow

1. Validate/store the source and start the existing background job with tenant/actor/budget context.
2. Inspect text/image/layout features and look up compatible stored patterns using inexpensive available evidence.
3. For an unknown layout, use AI extraction/structure discovery and save structured reusable rules, provenance and a candidate pattern version. Do not relearn every compatible upload.
4. For a known layout, apply versioned text/region/numbering/option/key/solution rules to the new source content, using deterministic/local work or compact AI context where appropriate.
5. Validate source coverage and type-specific output. Changed columns, numbering, missing options or ambiguous key/solution alignment remain visible.
6. On mismatch, drift or uncertain regions, fall back to AI on affected content or learn a new pattern/version. If model/budget access prevents this, preserve completed work and show an unresolved/waiting/failure outcome.
7. Continue shared staging, duplicate checks, correction and authorized QC/publication. A successful pattern match never means verified or published content.

Match at document/page/section level as needed. A matching header alone cannot establish full-document coverage. Never drop questions silently to claim fast-path success.

## Pattern data and lifecycle — design direction

Store stable pattern ID/version, scope/state, source/layout signature, script/language/context, section/column/region cues, numbering/option rules, answer-key/solution locations/alignment, asset/equation handling, parser/schema configuration and source/model/prompt/correction evidence. Protect example documents and actual answer content separately from structural rules.

Candidate/usable/deprecated/disabled states are proposed. P-22 now specifies candidate-to-usable after successful structural/coverage validation on discovery material, automatic selection of usable versions and visible drift/fallback. Numerical confidence/promotion thresholds require representative evaluation; none is claimed. The user requested automatic learning/reuse; do not add mandatory approval on every upload or defer the entire capability until samples arrive. Reuse requires structural validation and evidence; uncertain output remains reviewable.

Corrections may inform a new pattern version after separating layout mistakes from question-specific changes. Preserve versions used by earlier jobs and published questions. Disable/deprecate future selection without erasing history; concurrent discovery/retries need idempotency. Patterns are validated configuration, not arbitrary executable code generated by AI. Document instructions cannot change permissions, credentials or workflow.

## Reuse boundaries

A pattern is not an answer cache. Read every new question/answer/solution from its own source; never copy answers from the learning document. Exact-file retry caching, layout reuse, semantic duplicate detection and provider prompt caching are different mechanisms. Application pattern storage does not imply model fine-tuning or persistent model memory.

Each new handwritten/scanned image still needs recognition. Saved structure can reduce layout interpretation but cannot read unseen handwriting by itself. Preserve handwritten solution steps, equations, diagrams and question associations. No zero-token, zero-OCR or accuracy guarantee follows from pattern reuse.

Metadata and other AI stages may still consume tokens. Track recognition, structure analysis, fallback and other calls/costs separately; extraction-only savings are not automatically whole-job savings. Enabled models, coaching-owned keys, monthly limits and budget-stop rules remain.

Patterns are separate per coaching by default. Platform admin may explicitly share the complete coaching dataset, including patterns and associated material, with another coaching. There is no automatic platform-wide reuse. Sharing creates an independent initial copy; each coaching may modify/use its own patterns without synchronization. Destination users and API keys are configured separately, not copied with patterns; source/example provenance does not grant source-user membership or reuse source credentials. See [dataset sharing](CROSS_COACHING_DATA_SHARING.md).

## Evidence plan

Record pattern/version, bootstrap/reuse/fallback mode, matching evidence, affected regions, coverage/warnings, models/calls/tokens/costs, timings and correction results. Test new/repeated A, B, unseen C, layout drift, mixed pages, scans, handwritten questions/solutions and ambiguous/missing keys using separate learning/evaluation examples. Compare quality/completeness, correction effort, calls/tokens and time against comparable initial-AI processing, including recognition/fallback costs. Numerical thresholds and savings remain uncommitted; no evaluation has run.
